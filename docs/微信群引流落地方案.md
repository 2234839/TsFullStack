# 微信群引流服务（group-entry）落地方案

> 本文档是需求契约，交给 agent 按此实现。实现进度更新到本文档末尾「实现进度」段。

## 一、背景与目标

开源项目（silkpulse / TsFullStack / ccdd / mcpserver / vite-plugin-pilot）需要把 GitHub 用户引流到微信交流群。核心约束：

1. **微信群二维码 7 天过期**（进群上限 200 人，扫码上限 100 人/7 天）——不可能在 README 放静态群码
2. **博主拒绝定时维护**——没人进群时必须零操作
3. **README 一旦发布永不再改**——入口链接必须永久有效
4. 链路里唯一可用的永久锚点：**公众号二维码**（永不过期）+ **本项目动态服务**

## 二、总体链路

```
GitHub README（永不改）
  ├─ 图片形式：![](https://<域名>/group/<项目名>.png)   ← 动态图，README 内直接可见
  └─ 链接形式：https://<域名>/group/<项目名>            ← 落地页，人点开看
        ↓ 二维码有效时
当前微信群二维码（扫码进群）
        ↓ 二维码过期时
提示图/提示页：「群码已过期，关注公众号回复 加群 获取最新入口」+ 公众号二维码
```

维护模型（**事件驱动，非定时驱动**）：用户在公众号发「加群」→ 公众平台推送通知到博主微信 → 博主上传新群码（1 分钟操作）→ 服务自动恢复出码。**没有人进群 = 永远零维护。**

## 三、功能需求

### 3.1 动态图片接口（核心）

`GET /group/:entry.png`

- 二维码**有效期内**：直接返回该二维码图片（`Content-Type: image/png`，可被 GitHub README 缓存友好展示）
- 二维码**过期或缺失**：动态生成一张提示图返回（同样 200，不能 404——README 里的图裂了很难看）。提示图内容：简短文案「群码更新中，请关注公众号回复【加群】」+ 公众号二维码图
- 提示图的生成方式：**用 `sharp`（或 `@napi-rs/canvas`）把文案 + 预置的公众号二维码图合成一张 PNG**，不依赖浏览器渲染；公众号二维码图放静态资源，博主一次性上传

### 3.2 落地页接口

`GET /group/:entry`

- 有效期内：展示当前群码大图 +「长按/扫码进群」+ 该入口项目的说明
- 过期时：展示公众号二维码 + 引导文案「关注后回复 加群，我会收到推送马上更新」
- 落地页要**移动端优先**（微信内打开是主场景）；禁止依赖被墙资源（Google 字体等）

### 3.3 多入口区分

- `:entry` 即入口标识（`silkpulse` / `tsfullstack` / `ccdd` / `mcpserver` / `pilot` ...）
- 同一入口标识可绑定**多个微信群**（群满了换群不换链接）：后台配置 `activeGroupQR` 指向当前生效的那个
- 所有入口共享群码池（一个群多个入口用），但**独立统计**（见 3.5）

### 3.4 管理接口（无 UI，简单鉴权）

管理操作全部走 HTTP API + `x-admin-token` 头（token 走环境变量，拒绝弱默认值）：

- `POST /admin/qrcode` —— 上传新群码（multipart 图片 + 入口/群名 + 备注）。**上传时刻即生效时刻**，同时自动将旧码置为 archived
- `GET /admin/qrcodes` —— 列出群码池（含各码的 uploadedAt / expiresAt / 状态）
- `POST /admin/qrcode/:id/archive` —— 手动下线某码
- `GET /admin/stats?days=30` —— 引流统计（见 3.5）
- 上传成功后**回调通知博主**（server酱/bark，URL 走环境变量，可选）——形成「公众号推送 → 我上传 → 回执确认」的闭环

### 3.5 引流埋点统计

- 动态图和落地页分别记 PV；落地页额外记 UV（当日 cookie）
- 按 `entry` 维度聚合成 `stat_daily` 表：日期、入口、imgPv、pagePv、pageUv
- 目的：回答「哪个 repo 真的在带人进群」，指导后续在哪些项目投入

### 3.6 群码有效期规则

- 微信群码有效期 **7 天（168h）**，从上传时刻起算
- 服务端不主动判断「真过期」（无法探测微信侧真实状态），只按 `uploadedAt + 168h` 计算 `expiresAt`
- 提供 5 分钟粒度的边缘缓冲：到期前后 5 分钟内的请求按过期处理（宁早勿晚，用户扫到过期码的体验最差）
- 群码扫满 100 人（7 天内上限）时博主手动 archive 换新码，同「过期」逻辑

## 四、技术方案

### 4.1 落位

- 新建 `apps/group-entry`（独立小服务，不耦合 backend 主应用）：
  - NestJS 或裸 fastify 均可，**优先与 monorepo 现有栈一致**
  - 数据表 2 张：`group_qrcode`（id, entry, groupName, imageUrl/存储路径, uploadedAt, expiresAt, status, note）、`stat_daily`（date, entry, imgPv, pagePv, pageUv，联合主键 date+entry）
  - 图片存储：本地磁盘目录（`uploads/group-entry/`）起步，**不引入 OSS**；图片经管理接口上传后落盘，动态图接口直接流式返回
  - 提示图合成：`sharp` 叠加（底图纯色/渐变 + 文案 SVG 渲染 + 公众号码贴图），合成结果按公众号码版本缓存，避免每请求重绘

### 4.2 缓存策略

- 动态图接口：`Cache-Control: public, max-age=300`（5 分钟）——过期切换最多延迟 5 分钟可见，GitHub CDN 也能接受
- 落地页：`no-store`（保证最新状态）

### 4.3 部署

- 目标域名：现有服务域名下加路由前缀即可（如 `https://<已有域名>/group/...`），或独立子域
- HTTPS 必备（微信内打开 http 会拦截）
- 进程守护/systemd 或既有部署方案，上传目录持久化

### 4.4 安全

- 管理接口：`x-admin-token`（环境变量注入，缺失时管理接口整体禁用并打日志）
- 上传限制：仅 png/jpg/webp，≤5MB
- 动态图/落地页**不暴露任何群码原图路径**，统一经服务出图
- 统计接口仅管理 token 可访问

## 五、验收标准

1. README 放 `![](/group/silkpulse.png)` 后：有效期内显示群码；手动 archive 后 5 分钟内变为提示图（含公众号码）
2. 落地页手机微信内打开正常、两种状态切换正确
3. 上传新码后 1 秒内动态图恢复出群码
4. 未配置任何群码时，图片/落地页均优雅降级为公众号引导，**不 500、不 404**
5. `GET /admin/stats` 能按入口返回近 30 天 PV/UV
6. 主 README（5 个项目）各加一段「交流群」入口后，链接永不再变

## 六、明确不做（防 agent 过度发挥）

- 不做管理后台 UI（curl / hoppscotch 够用）
- 不做定时任务（无 cron、无轮询——过期判断是请求时惰性计算）
- 不接企微 / 不做活码平台对接
- 不做多用户 / 权限系统（单管理员）
- 不做群码自动检测是否真过期（无官方 API，不做玄学探测）
