# 多实例演进分析（2026-10-31）

> 背景：当前单实例 + SQLite + PM2 单进程。gs 拍板：安全状态不允许再依赖进程内存，要预留「类 Redis 接口层」演进路径。本文是全仓盘点结论与改造方案。

## 一、存量进程内存态清单（按多实例下的风险分级）

### A 级：多实例下必然出正确性/安全问题（安全状态）

| 位置                                                                 | 状态                                        | 多实例后果                                                         |
| -------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| `src/OAuth/github.ts` `oauthStates` Map（github/linuxdo 共用）       | OAuth state 登记表（10min TTL，一次性消费） | 负载均衡后回调落到另一实例 → state 查不到 → 登录全挂               |
| `src/api/appApi/passcode.ts` `mergeTickets` Map                      | 一次性合并票据（防账号接管）                | 回调与合并请求不同实例 → 票据失效；且防重放只对单实例成立          |
| `src/services/PasscodeService.ts` `verifyFailCache`/`verifyBanCache` | 口令验证失败计数/封禁标记                   | 攻击者请求被打散到 N 实例 → 限速阈值实际放大 N 倍                  |
| `src/api/appApi/auth.ts` `loginFailCache`/`ipFailCache`              | 登录失败递增延迟 + IP 封禁                  | 同上，爆破防护被稀释                                               |
| `src/api/appApi/passcode.ts` `passcodeCreateCache`                   | 匿名创建口令 IP 限流                        | 同上                                                               |
| `src/middleware/rateLimit.ts` `requests` Map                         | 通用请求限速                                | 限速被稀释                                                         |
| `src/server/authCache.ts` `userCache` + `userKeysIndex`              | 鉴权缓存（10min）+ 登出/合并失效            | 撤销只清本实例，其他实例最长 10min 陈旧 → 登出后其他实例仍认旧会话 |

### B 级：多实例下重复工作/轻微不一致（性能缓存，最终一致可接受）

| 位置                                                         | 说明                                                                                       |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `src/Context/AIProxyService.ts` `modelsCache`                | 模型列表 5min 缓存，各实例独立刷新，可接受                                                 |
| `src/server/groupEntry.ts` groupEntry cache                  | 同上                                                                                       |
| `src/services/WechatService.ts` accessToken/media/replyCache | 各实例独立取 token（微信侧多 token 并存可用，但浪费）；`appConfigByAppId` 等静态注册表无碍 |
| `src/lib/SessionAuthSign.ts` CryptoKey cache                 | 纯计算缓存，无碍                                                                           |
| `src/services/WechatCommandService.ts` `pendingImages`       | 短时 pending 去重，打散到多实例会重复下载（低危）                                          |

### C 级：进程级诊断/调度（天然单实例语义，多实例下各自采各的，无需改）

- `LoopLagMonitor`、`diagApi` 统计、`SpanCollector`
- `util/dbQueue.ts`：**DB 队列本身已按跨实例设计**（workerId/instanceId 校验、DB 心跳），是正确示范
- `TokenCleanupService` 等定时任务：多实例会重复执行，需在 dbQueue/DB 锁上收敛（切多实例时处理）

### D 级：不在演进范围内（gs 拍板 2026-10-31）

数据库层不需要在多实例改造中考虑：切多实例时会换非嵌入式数据库，或至少做代理把所有数据库请求收敛到单台数据库服务器——数据库一致性由那套基础设施解决，代码层的 ZenStack/Prisma 查询无需改动。

- SQLite 单写者 → 换库/代理方案，不在代码改造范围
- uploads 本地磁盘 → 同理由部署层解决（若未来落共享存储，只需替换 FilePathService/StorageType 实现，不改业务代码）
- 定时任务重复执行 → 切多实例时在 dbQueue/DB 锁上收敛（已有跨实例设计基础）
- **AI 限速已落 DB（AiCallLog）✓**——多实例安全的范本：安全状态落 DB 本身就是合法落地方式

## 二、接口层设计（KVStore）

所有 A 级状态收敛到一个 Effect Service，实现可替换：

```ts
/** 分布式 KV 原语：当前 LocalLayer（单实例内存），切多实例换 RedisLayer */
export class KVStore extends Context.Service<KVStore>()('KVStore', {
  /** 原子自增并返回新值（限速计数核心原语） */
  incr: (key: string, ttlMs: number) => Effect.Effect<number>,
  /** 读取（不存在返回 null） */
  get: (key: string) => Effect.Effect<string | null>,
  /** 写入带 TTL */
  set: (key: string, value: string, ttlMs: number) => Effect.Effect<void>,
  /** 删除（撤销/一次性消费） */
  del: (key: string) => Effect.Effect<void>,
  /** 原子 compare-and-delete：仅当值匹配才删（一次性票据防并发重放） */
  takeIfEqual: (key: string, expected: string) => Effect.Effect<boolean>,
  /** 按前缀删除（authCache 反向索引这类 key 集合失效） */
  delByPrefix: (prefix: string) => Effect.Effect<void>,
}) {}
```

- **LocalLayer**：已实现 `src/Context/KVStore.ts`（KVStore Tag + LocalKVStoreLive，已挂入 AppLive 与请求侧 Layer 树），含 TTL 惰性过期与容量淘汰
- **为什么不用 Effect Cluster**（调研 2026-10-31，effect.website Module of the Week 系列）：官方分布式方案 `effect/cluster` 是虚拟 Actor（Entity）编排框架——状态归属单个实体 + shard 路由 + 持久化消息/幂等键/outbox，解决的是「海量有状态实体串行处理」；我们的痛点是共享原子 KV（限速计数/一次性票据），Cluster 需要重构业务为 Entity+RPC+SQL 持久层，过重不对口。Effect 官方无 Redis 客户端/分布式 KV 原语，外部存储 + Tag/Layer 封装即是 Effect 惯用法。若未来出现按用户串行编排任务的需求再评估 Cluster（其幂等键/事务 handler/outbox 模式对现有 webhook 处理也有参照价值）
- **RedisLayer**：未来多实例时实现，接口不变；Redis `INCR+PEXPIRE` 天然对应 `incr`，`GETDEL`/Lua 对应 `takeIfEqual`
- 迁移策略：A 级逐个改为「key 约定 + KVStore 调用」，值统一 string（JSON 序列化），TTL 显式传入
- 鉴权缓存（authCache）特殊：除 KVStore 外还需「失效广播」——单实例=本地 del；多实例=Redis pub/sub 或干脆把鉴权结果也放 Redis 共享缓存（推荐后者，简单）

## 三、改造优先级（切多实例时，按序）

数据库/存储层不在范围（见 D 级说明），代码层只剩：

1. ~~A 级迁 KVStore~~ **已完成（2026-10-31）**：oauthStates（OAuth/github.ts）、mergeTickets（appApi/passcode.ts）、passcodeCreateCache（同上）、loginFail/ipFail（appApi/auth.ts）、verifyFail/verifyBan（PasscodeService）、tokenConsumeRateLimiter（middleware/rateLimit.ts 重写为 checkTokenConsumeRate）全部走 KVStore；顺带修复 LocalKVStore.incr 为固定窗口语义（TTL 仅首次自增生效，与原 Cache/RateLimiter 一致）。**authCache 仍留内存**（B 级性能缓存，允许最终一致；迁移时需配合失效广播，见上）
2. 定时任务收敛到 DB 队列（dbQueue 已有跨实例设计）

当前决定：约束已落（见 CLAUDE.md「多实例演进约束」）；A 级安全状态已全部收口 KVStore，存量仅剩 authCache（B 级）与 dbQueue 定时任务两项。
